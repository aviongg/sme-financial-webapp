## Runtime shape and boundaries

`backend/pom.xml` declares Spring Boot 4.1.1, Java release 21, Spring MVC, JPA, Spring Security, JDBC sessions, PostgreSQL/Flyway and mail. Pinned Tomcat/Jackson overrides are existing repository choices, not a fresh dependency-security certification. Domain packages form one Spring modular monolith. FastAPI in `ai-service/` is an OCR draft extraction boundary, not an existing financial copilot. No ledger, account balance authority, AR/AP allocation engine, inventory valuation service, salesperson scope, FX settlement service or FinancialQueryFacade exists in the inspected application.

Existing financial flow is session-resolved business → manual monthly snapshot or explicitly confirmed OCR contribution → `MonthlyRecordService` → `ScoringService` → persisted score/evidence → shared advice generation → dashboard/cashflow/search/WhatsApp consumers. Legacy `userId`/`user_id` in financial entities means **business ID**, not authenticated actor ID. `BusinessProfile.userId == Business.id` is a compatibility bridge. Identity `AppUser.id` is a different identifier. This distinction is mandatory for all future audit events, queries and foreign keys.

## Business identity, memberships and profile

`J/identity/entity/{Business,AppUser,BusinessMembership}.java` and their repositories separate account and business identities. `ActiveBusinessContext.getCurrentContext()` resolves the session-selected business, then checks current active account, active business and active membership in the database. Invalid selection is cleared. `BusinessAuthorizationService.requirePermission()` returns a server-derived `BusinessAccessContext(userId,businessId,role)`; controllers pass `businessId` into scoped domain repositories. Platform admin is a platform role, not blanket tenant financial access.

Session activation happens after service return/commit. `GET /api/businesses`, `GET/POST /api/businesses/active` list/select authorized businesses; `PATCH /api/businesses/active/name` is OWNER-only. ## Documents, OCR and source confirmation

`J/documents/entity/UploadedDocument.java`, `DocumentCorrection.java`, repositories, `DocumentResponse` and the three services separate original extraction, reviewed draft and confirmed contribution. The API returns structured metadata plus JSON strings for extracted/reviewed/confirmed data. OCR-derived source data is not automatically authoritative.

1. `POST /api/documents/upload` receives multipart file/type hint; `/bulk` accepts up to ten files. `DocumentUploadService` stores file metadata with status `pending`, saves the row and schedules processing **after commit**. Each file has a generated storage name under business/month; no client path is trusted.
2. `DocumentFileValidator` caps files at 10 MB, detects JPEG/PNG/WebP/PDF by signature and checks extension compatibility. `LocalFileSystemStorageService` normalizes paths, checks root containment/symlinks and writes through a temporary file/atomic move. Downloads require scoped `DOCUMENT_READ` and return `nosniff`, private/no-store. This is local-volume storage, not cloud document management or virus scanning.
3. `JpaDocumentDraftStore` atomically claims `pending → processing`. `DocumentDraftProcessor` calls `OcrClient`, stores complete high-confidence response as `extracted`, otherwise `needs_review`, and maps errors to `failed`. No worker can confirm. Configuration actually wires the processor through `J/documents/config/DocumentProcessingConfiguration.java`, despite older isolated-orchestration wording in a class comment. Without opt-in OCR client it deliberately fails unavailable.
4. `PATCH /api/documents/{id}` uses `DocumentReviewService`: locked business-scoped draft, supplied-field correction semantics, amount precision/scale and category/type validation, immutable before/after correction history, retained original extraction/confidence, correct actor/business audit. History is `GET /{id}/corrections`.
5. `POST /{id}/confirm` accepts `targetMonth`, positive `confirmedAmount`, optional date/party, target classification (`revenue|operating_expenses|cogs|none`), independent cash effect (`cash_inflow|cash_outflow|none`) and optional initial EOM cash. `DocumentConfirmationService` locks the scoped document, accepts only extracted/review states, calls `MonthlyRecordService.applyDocumentContribution`, records confirmed JSON/month/time, and commits once. Reconfirm is 409; confirmed source cannot be deleted or retried.
6. `POST /{id}/retry` requires draft-edit permission, rejects existing extraction/review, and limits retry of currently processing work until stale. `DELETE /{id}` is draft-only. Startup recovery changes all `processing` rows to `failed`/`processing_interrupted`; this assumes one worker/runtime lifecycle, not multi-node leases.

**Existing Python contract:** `ai-service/app/main.py` exposes health and multipart `POST /extract`, verifies header service secret with constant-time compare, rejects query-string secrets, rejects unconfigured auth, reads bounded chunks and sanitizes error output. `app/models.py` returns nullable date/amount/party, category, confidence and detected document type; unknown fields are forbidden. Amount serialization verifies faithful JSON-number representation. `app/service.py` caps concurrent extractions, retries transient provider failures at most three attempts, limits text. `app/documents.py` inspects bytes/image limits/PDF pages; current defaults 10 MB, 5 PDF pages, 25 million pixels, 100,000 text characters, four concurrent operations. `app/providers/google_cloud_vision.py` owns lazy Google SDK/ADC, explicit timeout and response/page verification. Provider output is normalized before deterministic parsing in `app/parser.py`.

**Java transport:** `J/documents/ocr/{OcrClientSettings,OcrIntegrationConfiguration,HttpOcrClient,JdkOcrHttpTransport,OcrJsonCodec}.java` use an opt-in configured internal endpoint, multipart bytes, shared service secret, response content/size/schema validation, no redirects and one transport attempt. Python owns provider retries. Production refuses plaintext OCR HTTP; configured CA controls trust. These are existing integration components, not proof of deployed HTTPS/provider credentials.

**Required future split:** B owns reviewed mappings/navigation (F12B); A owns a single idempotent C01/C02 financial contribution in ledger mode. Preserve snapshot-mode behavior and original source linkage. Never call both the existing incremental contribution and a ledger projection for one confirmed source. Same-document locking does not deduplicate two uploads of the same real invoice; source fingerprint policy is missing. Tests: `T/documents/service/`, `processing/`, `ocr/`, `storage/`, `DocumentSecurityPostgreSqlIT.java`, `DocumentProvenancePostgreSqlIT.java`, `Feature12PostgreSqlIntegrationTests.java`; Python `tests/test_api.py`, `test_documents.py`, `test_parser.py`, `test_vision_provider.py`.

## Search and Zakat

`J/search/controller/SearchController.java` accepts `POST /api/search` (`SearchRequest` query/type), requires financial read and conditionally document permission. `SearchService` gathers only business-scoped persisted monthly records (legacy result type `transaction`), insights, recommendations, scores and permitted document metadata; `SearchResultRanker` ranks then caps at 20. Blank query returns empty without repository reads. Original filenames use existing decryption; OCR text is intentionally not searched. Result DTO includes ID/title/description/type/date/amount/category/href/badge. This is application search, not natural-language finance queries, raw SQL or a ledger. It loads all eligible rows before ranking; scale requires bounded queries/indexes when Phase 2 volumes grow. Search monthly descriptions format integer PKR and use zero for null display fields; do not reuse their display formatter as numeric evidence for FX/AI. Tests: `T/search/`.

`J/zakat/controller/ZakatController.java` has authenticated stateless `POST /api/zakat/preview` (no active business needed) and tenant-derived `/monthly/preview` requiring `ZAKAT_READ_CALCULATE`. `ZakatService` loads the requested monthly record and reconciles classified receivables to its outstanding balance. `ZakatCalculationService` returns policy/version, inputs/source, inclusion/deduction breakdown, missing/warnings, net assets/nisab/due/status and financing disclosure. The **existing code policy** is `HANAFI_PK_BUSINESS_V1` 1.0.0, silver weight 612.36g, rate .025, current payables plus qualifying principal; price/source/time and haul are supplied, not invented. Unsupported/ambiguous categories can return incomplete/manual-review instead of a fabricated due amount; raw material/WIP do not automatically inherit a trading inventory rule. This audit reports implementation, not independent religious or tax advice. F08/F03 must keep source reconciliation and require policy review before extending valuation/obligation mappings. Tests: `T/zakat/`.

## Phase 2 reuse decision

Reuse authentication/MFA/session/CSRF, account/business/membership identity, profile onboarding, monthly/scoring/evidence/history, advice/action status, OCR draft/review/confirmation lifecycle, search controls, Zakat policy engine, WhatsApp opt-in/outbound lifecycle, audit and encryption. Extend these through the agreed C01–C12 contracts. New accounts/posting, obligations/allocations, cash plans, commissions/row scope, FX, reconciliation/import/recurrence and C11 query tools remain **proposed A-owned work**. B must consume these authoritative outputs, not recreate them inside invoices, project analytics, widgets or AI.
