# Developer A financial platform package specifications

These are proposed designs, **not implemented features or frozen financial contracts**. A leads every package here and B reviews/consumes. They are included so B's independent chats can identify real prerequisites; they do not authorize B to implement A's domains. Contract DTO field types, examples, nullability, errors, transitions and versioning are specified in [C01–C12](../INTEGRATION_CONTRACTS.md); unresolved accounting choices are [P01–P14](../FINANCIAL_POLICIES.md). No package is DONE.

Paths below use `J=backend/src/main/java/com/app/sme_health_backend/`, `T=backend/src/test/java/com/app/sme_health_backend/`, `F=frontend/src/`. Classes/tables/endpoints called proposed are candidates for implementation. All use existing session/CSRF/ActiveBusinessContext/BusinessAuthorizationService, scoped repository queries and fail-closed SecurityAuditService. New UUID/business FK, `version`, source identity, decimal-string DTO, index and additive migration rules are inherited from the master contracts. Existing `/api` contracts remain intact.

## F01 Transaction-Based Financial Management

1. **Lead/support:** A/B; owns C01/C02 and the canonical category/account/posting model. Priority W1, prerequisite for actual financial integrations.
2. **Objective/workflow:** owner selects source mode and reconciles opening balances; authorized user records income/expense/transfer, reviews posted evidence, reverses an error, and sees the resulting monthly record and unchanged scoring methodology.
3. **Reuse:** `J/records/{entity/MonthlyRecord,service/MonthlyRecordService,repository/MonthlyRecordRepository}.java`, `J/scoring/service/ScoringService.java`, `J/shared/advice/`, `J/audit/service/SecurityAuditService.java`, `F/lib/api/finance.ts`, live monthly forms and financial display components. Reuse scoring once, not each component in a new ledger.
4. **Missing:** accounts, categories, posting journal/movements, source deduplication, reversal, cutover, projections/watermarks, opening reconciliation and transaction UI. Search result type `transaction` currently means monthly record and is not evidence of a ledger.
5. **Proposed backend:** `J/ledger/{entity/FinancialAccount,FinancialCategory,FinancialEvent,AccountMovement,PostingReceipt,FinancialSourceMode,MonthlyProjectionState}.java`; scoped repositories; `service/{PostingService,AccountBalanceService,FinancialSourceService}.java`; `projection/MonthlyProjectionService.java`; DTOs `PostingCommand`, `PostingReceiptResponse`, `CutoverPreviewResponse`; controllers `TransactionController`, `AccountController`, `FinancialSourceController`. C02 adapter invokes existing monthly/scoring pipeline without exposing unrestricted monthly writes.
6. **Schema/migrations:** `financial_accounts` tenant/name/currency/type/status; `financial_categories` stable semantic key; `financial_events` tenant/source/revision/effective date/original/base/policy/reversal FK; `account_movements` tenant/event/account/direction/exact amount; `posting_receipts` operation/key/hash/result; `financial_source_modes` one per business with cutover and base currency; `monthly_projection_states` unique tenant/month with source watermark/hash/status. Unique tenant/source/revision/effect and tenant/idempotency operation/key; indexes tenant/effective-date/id and tenant/account/date. Composite tenant FKs prevent cross-business relations. Migration reservations split schema, constraints/grants and compatibility/backfill only as needed; no fixed V18 claim.
7. **Authority:** PostingService owns recognized effects; AccountBalanceService owns account sums; projector owns monthly mapping. Sum signed movements for cash accounts, exclude internal transfers from operating flows per reviewed C02 rule, preserve null unsupported fields and compute stocks as of period end. Existing score formula and rescore window remain. Posting/projection consistency policy P02 must decide atomic derivation versus durable stale state.
8. **API:** `/api/v2/accounts` creates/lists accounts from `{name,type,currency}`; `/categories` exposes canonical read catalog; `/transactions` accepts C01 facts and idempotency, returns immutable event/effects/source; `/{id}/reverse` accepts reason/version/date and returns compensating receipt; `/financial-source/cutover-preview` accepts C02 openings, returns conflicts/differences; `/cutover` commits approved preview; `/monthly-projections/{month}` returns basis/record/status. Server never accepts a new authoritative balance supplied by a display widget.
9. **Frontend:** proposed `F/app/accounts/page.tsx`, `transactions/page.tsx`, `transactions/[id]/page.tsx`, `settings/financial-source/page.tsx`; account selector, validated decimal amount, category, date, source evidence, transfer paired-account form, reversal confirmation, cutover comparison. Existing `/records/new` remains snapshot-only for eligible months. Add `F/lib/api/transactions.ts` via same-origin client and localized permission/module-aware navigation.
10. **Auth:** proposed account/post/reverse/cutover permissions require reviewed mapping. OWNER setup, ACCOUNTANT financial operations only as approved; MANAGER/VIEWER cannot gain writes. Tenant context for every query; audit real actor and business. C08 later narrows row scope without granting full account access.
11. **Interactions:** F03 settles through C01; F04 creates obligations through C04; F08 sends approved cost effects; F12A import/recurrence uses same command; OCR uses either snapshot or ledger route; all existing score/advice/dashboard/Zakat readers use compatible monthly projection.
12. **Rules/edges:** no historic transaction fabrication; one source mode per month; transfers neutral; reversals append; backdates update later closing balances and dependent score windows; openings do not become revenue; duplicate sources through OCR/invoice/import count once; overflow/overdraft/closed month explicit. Cross-document current snapshot races and incorrect audit attribution must be addressed in an authorized scoped follow-up, not copied into new logic.
13. **Tests/UAT:** exact arithmetic and mode mapping; PostgreSQL parallel posting/reversal/unique constraints; replay/rekey/conflicting hash; fresh+V17 upgrade; cross-tenant account refs; projector rebuild equality; unchanged 18 numerical score fixtures; real owner creates/reverses transaction and sees source-linked month/score, legacy user retains snapshots. Include failed audit/scoring compensation behavior.
14. **Dependencies:** freeze C01/C02, early C09 currency semantics and P01/P02/P10/P14. Can design catalog/fixtures first; actual integrations cannot consume a mock ledger. B can independently implement F02 after its own contracts freeze.
15. **Complexity:** finance 5/5, integration 5/5, DB/concurrency 5/5, UI 4/5. Critical path; split into reviewed account/source-mode, posting, projection and cutover slices, each with real independent acceptance rather than declaring the whole feature complete early.
16. **DoD:** authorized full journey and migration upgrade pass; source graph/rebuild reconcile; old snapshots and score fixtures unchanged; concurrent/replay/denial tests pass; en/ur/mobile UI and actual backend verified; A/B signoff, docs/state and remote commit recorded.

## F03 Receivables, Payables and Payment Cycles

1. **Lead/support:** A/B, C04, W2.
2. **Workflow:** create customer/supplier and terms; inspect obligations/ageing; record partial receipt/payment or advance; allocate to eligible obligations; review residual and audit/source trail.
3. **Reuse:** business context/security, BigDecimal conventions, profile's declared payment behavior for existing score only, `MonthlyRecord.receivablesOutstanding/payablesOutstanding`, shared UI tables/forms, C01 accounts. Existing nullable balances are not obligation rows.
4. **Missing:** counterparty register, obligations/credits, payment allocations, advance/refund lifecycle, ageing and actual collection statistics.
5. **Proposed classes:** `J/obligations/entity/{Counterparty,Obligation,ObligationAdjustment}.java`, `service/{CounterpartyService,ObligationService,AgingService}.java`; `J/payments/entity/{Payment,PaymentAllocation}.java`, `service/PaymentAllocationService.java`; controllers, scoped repositories and C04 DTOs. One outstanding calculator inside ObligationService.
6. **Schema:** counterparties with tenant/type/contact/terms; obligations with direction/source/document/due date/original/base/rate/status/version; payments with account/posted event/date/currency; allocations with tenant/payment/obligation/amount and reversal linkage; adjustments preserve credit/refund reason/source. Unique tenant/source/revision for obligation; allocation retry uniqueness; indexes tenant/direction/due-date/status and tenant/counterparty/date. Lock payment and obligations in deterministic order; composite FKs, amount bounds, version checks and grants in reserved migrations.
7. **Calculations:** outstanding=principal−valid credits−allocations under P03; ageing uses reporting-date buckets on residual only; expose unallocated advance distinctly; account movement comes from C01. Observed payment cycles may be an additional metric, not a replacement of v1 declared repayment score.
8. **API:** C04 `/counterparties` CRUD/archive with validated name/type/terms; `/obligations?direction&asOf&counterpartyId&cursor` returns typed residual/buckets; `/payments` takes account/date/money/allocations and returns payment/event/residual advance; `/{id}/allocations` allocates existing residual with version; reversal/credit commands require reason and original source. Never accept client-supplied outstanding as authoritative.
9. **Frontend:** proposed `F/app/counterparties`, `receivables`, `payables`, `payments` pages and detail views; allocation dialog shows eligible obligations, paid/remaining values and currency; ageing drilldown and explicit unavailable/stale/error states. Invoice screen links these results instead of owning settlement logic.
10. **Auth:** reviewed obligation-read/payment-post/refund permissions; scoped lookups even when two counterparties share names; no membership invited/suspended access; later sales scope filters both detail and total endpoints.
11. **Integrations:** B F04 issue source creates obligation; C01 money movement/C02 stocks; C06 plan replacement; C09 mixed currency; calendar/query tools consume dates and residuals.
12. **Edges:** zero/negative payment, partial and over-allocation, advance/refund, due-before-issue, same-day cutoff, cancelled/credited invoice, party mismatch, parallel settlements, original/base currency separation. No cash at document issue, no paid-status hand edit.
13. **Tests:** bucket boundaries; residual conservation; PostgreSQL concurrent allocation and retry; reversal restores correct outstanding; cross-tenant IDs; source issue/payment integration with F04; owner/accountant partial-payment browser journey and forbidden viewer write.
14. **Prerequisites:** C01 producer, C04/P03/P04/P10 freeze; F04 document integration later needed for full combined story, but direct authorized obligations can be an explicit useful slice. B draft documents may proceed without pretending payments are available.
15. **Complexity:** finance 5, integration 5, DB 5, UI 4; critical W2 prerequisite for projects/funding/FX.
16. **DoD:** obligations, partial payments, advances/refunds and ageing reconcile with ledger/month; real authorized UI journey, numerical/DB/security tests, tenant-safe linked invoices, A/B acceptance and verified remote handoff.

## F07 Project Cash Flow and Funding Gap

1. **Lead/support:** A/B, C06; B owns project identity, economics and budget.
2. **Workflow:** choose approved project budget, schedule dated expected receipts/outflows, compare actual settlement, vary timing/amount in a nonposting scenario, view peak funding and recovery date with assumptions.
3. **Reuse:** `J/cashflow/calculator/TrendProjectionCalculator.java` only for its historical trend purpose, C05 project/budget DTO, C04 settlements, existing chart/UI patterns. Historical regression is not the funding engine.
4. **Missing:** dated plans, matching actuals, residual schedule, cumulative cash timeline, funding/scenario calculation.
5. **Proposed classes:** `J/projectcash/entity/{ProjectCashPlan,CashPlanLine,PlanSettlementLink}.java`, `service/{ProjectCashPlanService,FundingGapCalculator,ProjectScenarioService}.java`, controller and C06 DTOs. Calculators accept immutable typed inputs and return no side effects.
6. **Schema:** plan tenant/project/budget revision/version/approved basis; lines date/direction/original/base/source plan line; matching links authoritative settlement/allocated amount; optional saved scenario snapshot references plan revision. Unique tenant/project/revision, plan-line/settlement link identity; indexes tenant/project/date. Currency/rate and composite tenant FKs; additive migration reservation after C05 freeze.
7. **Authority:** replace settled portion of plan, compute daily cumulative available cash; peak shortfall and first recovery under explicit P11 definition. No B recomputation. Project profit remains C05; receipt timing is not recognized revenue timing.
8. **API:** C06 `PUT /projects/{id}/cash-plan` validates lines/dates/budget revision and returns accepted plan/version; `GET .../funding-gap?asOf&horizon` returns daily points, actual/planned basis, peak/date/recovery/assumptions; `POST .../funding-scenarios` returns comparative result from typed timing/amount overrides without posting.
9. **Frontend:** `F/app/projects/[id]/cash-flow/page.tsx`, dated schedule editor, actual links, funding timeline and scenario compare form; ambiguous missing dates and unallocated starting cash shown as actionable incomplete states.
10. **Auth:** project read/plan edit permissions and C08 row scope; no implicit reveal of owner's business-wide cash to a salesperson. References must resolve in active business.
11. **Interactions:** B F05/F06/F09 supply plan/category IDs; F03 supplies actual receipts/advances; F11 supplies base amounts; B dashboard/report/AI consume outputs.
12. **Edges:** partial settlements, date shift, no recovery, same-day netting, overdue unpaid schedule, cancelled project, currency missing, zero horizon and stale budget. Starting cash allocation cannot double-allocate one cash pool across projects without disclosure.
13. **Tests:** opening 0/outflow 200 then receipt 300 gives peak 200; early partial advance reduces only matching plan residual; irregular dates and no-recovery; scenario does not change ledger/month; PostgreSQL matching uniqueness and tenant denies; real schedule→actual→chart journey.
14. **Dependencies:** C05 identity/plan contract can freeze early for calculator fixtures; live funding requires real projects, C01/C04 and P11. A can build pure calculator tests while B builds project persistence, but cannot declare production integration complete from those tests.
15. **Complexity:** finance 5, integration 5, DB 3, UI 4; W3, follows stable project IDs and settlement data.
16. **DoD:** actual versus planned visibly separate; funding amounts and matched residuals reconcile; scenario nonmutation/authorization verified; project UI/live service/evidence usable and reviewed by B.

## F11 Multi-Currency, FX and International Payments

1. **Lead/support:** A/B, C09, full W5 but currency schema/policy needed in W0/W1.
2. **Workflow:** record original-currency invoice/expense with locked base rate, receive/pay partial international settlement and fee, inspect original/base residual and realized FX/source evidence.
3. **Reuse:** exact decimal domain conventions, C01/C04 amounts/accounts and existing transport. Existing `MonthlyRecord` and `CurrencyInput` are not multicurrency authorities; legacy PKR display must remain truthful.
4. **Missing:** currency registry/base choice, historical lock, settlement carrying-value release, gain/loss, fees and original/base reports. No provider rate feed is assumed.
5. **Proposed classes:** `J/fx/entity/{FxRateLock,FxSettlement,SettlementFee}.java`, `service/{FxRateLockService,SettlementService,FxCalculationService}.java`, C09 DTO/controller. One FX calculation implementation.
6. **Schema:** tenant rate lock pair/base-per-original/effective/source/locked timestamp; settlement obligation/payment/gross/net/fee/original/released basis/realized amount/policy/source key; indexes tenant/date/currency and obligation; immutable lock rows and composite FKs, exact money/rate bounds. Never overwrite historical locks from a new current rate.
7. **Authority:** convert using explicit direction and approved scale; proportionally release historical carrying value with final residual reconciliation; derive gross minus fee cash and direction-specific realized gain/loss. Do not classify fees as FX difference to hide costs.
8. **API:** C09 `/fx/rate-locks`, `/settlements/preview`, `/settlements`; requests identify obligation, original settled amount, actual gross receipt/payment, fee/account/date/rate/version; preview returns deterministic gross/net/carrying/released FX and warnings, commit locks the same basis or rejects stale. Read settlement detail returns immutable links and evidence.
9. **Frontend:** `F/app/settlements/page.tsx`, detail/preview dialog on invoice/payment; explicit currency selector/decimal-string input and locked rate direction/source/date; separate fee/gain/loss values; existing monthly reports label base currency.
10. **Auth:** settlement/rate permissions reviewed, active-tenant account/obligation, immutable approved rate access; no arbitrary external rates from client as trusted market fact; later salesperson rows restricted.
11. **Interactions:** F04 original totals, F03 allocation, F01 posting/C02 base projection, B estimate assumptions versus actual lock, project/report/query output.
12. **Edges:** inverse/zero rate, partial cents residual, cross-currency allocation, multi-fee provider settlement, cancelled invoice, refund at different rate, fee greater than gross, base-currency change and unsupported currency. Automated foreign bank execution and unrealized revaluation are not silently included.
13. **Tests:** C09 synthetic USD100/PKR28000 basis→28500 gross−500 fee gives 28000 cash and separately 500 gain/500 fee for receivable policy; payable sign fixture; partial releases sum exactly; concurrency/retry and tenant FK checks; exporter browser/API journey with report reconciliation.
14. **Prerequisites:** C01/C04/P10/P04 freeze; source/original/base fields agreed before invoice schema. Rate provider ADR and live acceptance only if subsequently requested.
15. **Complexity:** finance 5, integration 5, DB 4, UI 4; defer full implementation to W5 without deferring initial data semantics.
16. **DoD:** original/base history preserved, exact settled/residual/gain/fee numbers reconcile, actual authorized UI and projections verified, supported currency limits disclosed, B review and remote evidence recorded.

## F12A Financial Operations

1. **Lead/support:** A/B; financial import, reconciliation and recurrence; B F12B owns reporting/calendar/document experience.
2. **Workflow:** stage bank/transaction import, validate and resolve candidate duplicates, explicitly post accepted rows, match bank lines to existing movements, mark reconciliation with difference explanation; configure recurring proposals and approve generated occurrences.
3. **Reuse:** document validation/storage concepts, C01 source/idempotency, security audit and backend scheduler patterns. Existing OCR upload is not a bank importer; existing WhatsApp scheduler is not a financial recurrence authority.
4. **Missing:** import schemas/staging/dedup, bank statement lines/matches, reconciliation sessions, recurring financial rules/occurrences and traceable operation UI.

Delegate actual finance to PostingService/PaymentAllocationService.
6. **Schema:** batch file digest/mapping/version/status; row source reference/normalized data/validation state; bank line unique tenant/account/provider reference (fallback fingerprint under reviewed policy); matches with allocated amount and target posted event; reconciliation account/period/opening/closing/status/version; recurrence rule schedule/timezone/template/version and unique rule/due-date occurrence. Index tenant/account/date and batch/status. Composite FKs, immutable posted source, bounded file storage, no import rows automatically made actual by migration.
7. **Authority:** reconciliation compares bank facts to C01 account movements, not a second cash register. Recurrence generates idempotent drafts or approved commands under P02/P14; never uncontrolled duplicate financial jobs. Difference is explicit and does not create balancing income automatically.
8. **API:** `/api/v2/imports` multipart/map preview returns row errors and candidate duplicates; `/{id}/confirm` selects validated IDs/version and returns source/posting receipts; `/reconciliations` starts account/period/opening/closing basis; `/{id}/matches` links bank row/movement with amount; `/{id}/complete` returns reconciled difference and unmatches or blocks; `/recurring-rules` takes schedule/timezone/typed template and yields next dates, while occurrence approval invokes C01. Paginate large batches.
9. **Frontend:** `F/app/operations/imports`, `reconciliation`, `recurring` pages; review mapping/errors, duplicate compare, unmatched/matched amounts and residual; preview future occurrences, pause/resume with clear actual versus draft status. CSV formula injection protected in exports owned by B F12B.
10. **Auth:** financial-operations/import-post/reconcile permissions reviewed; file download and row scope tenant-bound; background occurrences use explicit system business context, audit minimized data; scheduler must recheck rule/business status.
11. **Interactions:** C01/C02 actual source, C04 payment matching, C09 rates, B document vault/calendar/report sees operation IDs/status without owning posting. Imported OCR/invoice/bank lines link common economic source graph.
12. **Edges:** duplicate file with changed filename, duplicate row with new key, legitimate equal payments, mismatched balance, split match, wrong currency, pending bank item, partial batch failure, DST/month-end recurrence, multiple worker race, cancelled rule and retry after timeout. Reconciliation completion locks reviewed basis and supports auditable reopening policy.
13. **Tests:** bounded/malformed file parsing, format/digest duplicate rules, partial-batch atomic policy, exactly-once occurrence under concurrent workers, cross-tenant matches and storage path, no auto-adjust on discrepancy; real import review→post→bank match→reconciled report journey and rerun.
14. **Prerequisites:** C01/C02/C04/C09 supported subset, P02/P14 plus account/source policies. Parser fixtures/staging UI can be useful independently, but posting/reconciliation cannot be called complete without authoritative movements.
15. **Complexity:** finance 4, integration 5, DB/concurrency 5, UI 4; W5, import integrity may need earlier design for F01 dedup.
16. **DoD:** reviewed import creates each source once; reconciliation exposes and resolves explainable differences; recurrence retries safe; live UI/DB/security/rollback tests pass and B document/report integration signed off.

### Supporting package implementation details

The table above defines owner, objective, reuse, gap, classes, schema direction, calculation, API, integration, prerequisites, complexity and DoD. The following details complete the frontend, data, authorization, edge and test requirements for each supporting slice; all are proposals.

**S-A01 financing/scenarios.** Request `{principal:Money,startDate:Date,termMonths:int,repaymentFrequency:MONTHLY,rate:Decimal,rateConvention:string,fees:Money,scenarioOverrides:object,policyVersion:string}`; response `{schedule:[{date:Date,principal:Money,interest:Money,fees:Money,remainingPrincipal:Money}],totalCashCost:Money,incrementalCashEffect:Money,assumptions:string[],evidence}`. Supported finance convention must be approved under P11; unknown product/convention yields unavailable, never an invented lender quote. Proposed `financing_scenarios` stores tenant/source watermark/typed input JSON schema version/result version/creator, indexed business/date; immutable saved revision, or stateless preview first with no migration. A owns `ScenarioController` and numeric tests; B integrates proposed `F/app/planning/scenarios/page.tsx` and `FinancingScenarioForm/ScenarioComparison` with permission-bounded cash data. Use explicit `SCENARIO_READ/SCENARIO_RUN` capabilities reviewed by A; no financial writes. Tests include approved amortization/fee fixtures, final principal residual, flat versus reducing-balance distinction, invalid rates/term, no history, cross-tenant source and repeat preview nonmutation. Done requires real authorized form/API, reconciled schedule and disclosure of assumptions, not a static chart.

**S-A02 advanced forecast.** Request `{asOf:Date,horizonDays:int,scenarioId:Id|null,includeSources:string[],assumptionsVersion:string}`; response daily typed expected/actual amounts and opening/closing cash with evidence, per-source unavailability and explicit uncertainty method. Preserve existing historical projection endpoint; new controller `AdvancedCashForecastController` calls the one source assembler/calculator. Optional `cash_forecast_snapshots` stores business/asOf/horizon/source watermark/assumption version/result, index business/asOf; source inclusion must be auditable and bounded. Proposed B `F/app/planning/forecast/page.tsx`, `ForecastTimeline`, `ForecastAssumptions`, and F13 widget; preserve mobile accessible data table and EN/UR distinction between forecast/actual. Require financial-read plus any restricted source scope; a narrow salesperson scope cannot use an unrestricted business forecast. Tests require known inflow/outflow dates, uncertain collection, overdue residuals, one invoice appearing in both project plan and AR, recurrence overlap, discontinuous history, stale snapshots and source correction. Done requires all supported sources reconcile and unsupported sources are explicit; no predictive-quality claim without a separately measured evaluation.

**S-A03 alerts/anomalies/risk.** Rule definitions include stable key/version, allowed metric/unit, minimum observations, threshold/window/severity, cooldown, scope and explanation key.
