## Shared wire and service rules

These proposed conventions apply to C01–C12. A contract section inherits all rules here unless it explicitly specializes them. New HTTP resources use `/api/v2`; existing `/api` DTOs and endpoints retain their contracts. This namespace is a proposal to freeze under C12, not an existing router.

* Resolve `BusinessAccessContext` through existing `BusinessAuthorizationService`; session cookies, MFA stage, CSRF and active membership remain mandatory. Never accept a financial request's tenant from JSON, an LLM, a URL business parameter or a phone number alone. Internal methods receive a server-created authorized context. Check every referenced ID belongs to that business; absent/cross-tenant resources return the same 404. Permission failures return 403. A module toggle never grants a permission.
* `Id` is a UUID string; `Date` is ISO `YYYY-MM-DD`; `Month` is `YYYY-MM`; timestamps are UTC ISO instants in **new** contracts. Legacy local timestamps retain their current interpretation until a separate migration decision. A business reporting timezone must be explicit for period cutoffs.
* New `Decimal` values are plain base-10 strings, without exponent/group separators; validate precision and bounds server-side and use Java `BigDecimal`. `Money={amount:Decimal,currency:string}` where currency is a supported uppercase code. Suggested storage is `numeric(19,4)` for new amounts, `numeric(19,6)` for quantities and unit costs, `numeric(24,12)` for rates; these are draft capacity choices, not adopted rounding/recognition policy. Existing `numeric(14,2)` monthly fields and numeric JSON remain unchanged. Projection rejects overflow and applies only an approved rounding adapter. Never round each intermediate silently.
* Fields are required/non-null unless marked `?` (omittable) or `|null` (present but unknown/unavailable). Optional update fields mean unchanged; explicit null clears only a documented nullable field. Zero is an observed amount, never a substitute for missing data. Signed flows use explicit direction or a signed effect, never both ambiguously.
* `SourceRef={type:string,id:Id,lineId:Id|null,revision:int}` is immutable after posting; `Evidence={sourceRefs:SourceRef[],asOf:Instant,period:{from:Date,to:Date}|null,sourceMode:SNAPSHOT|LEDGER|PLAN,methodologyVersion:string,completeness:COMPLETE|PARTIAL|UNAVAILABLE,missingFields:string[]}`. Empty evidence cannot substantiate an available financial answer.
* Queries return `{data:T|null,status:AVAILABLE|PARTIAL|UNAVAILABLE,reasonCode:string|null,evidence:Evidence}`. Authorization denial is an HTTP error, not leaked partial data. Restricted AI tools may return a safe `RESTRICTED` result without IDs or values. A legitimate zero can be AVAILABLE. Paging is bounded `{items:T[],nextCursor:string|null}`; stable ordering includes ID. Scope filters cannot widen permission.
* Mutations use a client-generated opaque `Idempotency-Key` (bounded length) and a version for mutable aggregates. Internal commands carry the same key. Store a unique `(business_id,operation,key)` and normalized payload digest; identical retry returns the original response, changed payload yields 409 `idempotency_conflict`. Source-effect uniqueness is additional: a fresh key cannot repost the same source revision. Concurrent version mismatch yields 409 `stale_version`. Database transaction plus row locks/unique constraints must decide races, not prechecks alone.
* Common errors retain existing `ApiError` compatibility: `{timestamp,status,error,message,errors?}` where `errors` maps field names to localized-safe text. New stable codes: `invalid_input` (400), `unauthorized` (401), `forbidden` (403), `not_found` (404), `invalid_transition`, `dependency_unavailable`, `policy_not_approved`, `source_mode_conflict`, `stale_version`, `idempotency_conflict` (409), `too_many_requests` (429 plus Retry-After), `service_unavailable` (503). No stack traces, storage paths or tenant existence leaks. Use current transport's no-auto-replay behavior for financial writes.
* Financial state change, source linkage, idempotency receipt and mandatory audit commit atomically. Audit records must contain the real actor user ID **and** business ID; legacy variable names `userId` in financial entities mean business IDs. Do not copy that ambiguity into new services. Durable source references and reconciliation totals are separate from generic security logging.
* Contract version is `1.0-draft`; no compatibility promises until frozen. After freeze, additive optional fields are minor versions; meaning, nullability, enum and rounding changes require owner/reviewer approval and consumer tests. Never silently reinterpret a historical event; record policy versions. No networking between Java modules is necessary: service interfaces in the existing Spring application can implement these contracts.

## C01 Transaction event and posting

**Interface:** proposed `ledger.service.PostingService.post(context, PostingCommand)`; `POST /api/v2/transactions`, `POST /api/v2/transactions/{id}/reverse`, `GET /api/v2/accounts/{id}/movements`. A owns event persistence, accounts, source registry and category semantics. B supplies reviewed commercial source facts; B never writes monthly balances directly in ledger mode.

`PostingCommand`: `occurredOn:Date`, `eventType:string` from frozen catalog, `source:SourceRef`, `categoryId:Id|null`, `projectId:Id|null`, `original:Money`, `fxLockId:Id|null`, `movements:{accountId:Id,direction:IN|OUT,amount:Money}[]`, `recognitionCode:string`, `policyVersion:string`. No caller-computed cash balance, project margin or base conversion accepted. For noncash recognition `movements=[]`; that does not imply zero recognition. Transfer requires two account movements and a transfer classification that excludes revenue/expense. Catalog must distinguish obligation recognition, settlement, inventory cost and opening balance events.

`PostingReceipt`: `eventId:Id`, `status:POSTED|REVERSED`, `source:SourceRef`, `base:Money`, `cashEffects:{accountId:Id,signedBaseAmount:Decimal}[]`, `recognitionEffects:{metric:REVENUE|OPERATING_EXPENSE|COGS|OTHER,signedBaseAmount:Decimal}[]`, `affectedMonths:Month[]`, `policyVersion:string`, `version:int`. Actual recognized effects are decided by A using approved domain policy. Draft documents/plans cannot invoke an actual event type without the relevant lifecycle transition.

Example (synthetic, IDs abbreviated here and below as `uuid-*` for readability; fixtures must use valid UUIDs): request `{occurredOn:"2026-10-10",eventType:"CASH_EXPENSE",source:{type:"manual",id:"uuid-source",lineId:null,revision:1},categoryId:"uuid-category",projectId:null,original:{amount:"100.00",currency:"PKR"},fxLockId:null,movements:[{accountId:"uuid-cash",direction:"OUT",amount:{amount:"100.00",currency:"PKR"}}],recognitionCode:"APPROVED_EXPENSE_POLICY",policyVersion:"pending"}` → receipt cash effect `-100.00` and operating-expense effect `100.00` **only after policy approval**. Sending `policyVersion:"pending"` to a future production service must fail closed.

Transitions: a draft source may post once; POSTED is immutable; reversal creates a compensating linked event and changes read status, never deletes the event. Reject duplicate reversal, wrong business account, disabled posting capability, closed/legacy period, unfrozen recognition policy and unbalanced transfer effects with 409/400. Proposed explicit `TRANSACTION_POST`/`TRANSACTION_REVERSE` permissions require reviewed role mapping. Tests: same-key/rekey replay, concurrent source posting, atomic rollback including audit, transfer neutrality, cross-tenant FKs, reversal reconciliation, decimals/overflow, no plan posting. Dependencies: policies and C09 base-currency semantics; no implemented C01 yet.

## C02 Monthly projection and cutover

**Interface:** `ledger.projection.MonthlyProjectionService.project(context, month, expectedSourceRevision)`; cutover preview/commit via `POST /api/v2/financial-source/cutover-preview` and `/cutover`. Queries `GET /api/v2/financial-source` and `/monthly-projections/{month}`. A owns both source mode and the sole ledger-to-month mapping.

`CutoverRequest`: `cutoverMonth:Month`, `baseCurrency:string`, `openingBalances:{accountId:Id,amount:Money}[]`, `openingObligations:SourceRef[]`, `inventoryOpeningSnapshot:SourceRef|null`, `previewVersion:string`, `policyVersion:string`. Preview reports `conflicts:{month:Month,reasonCode:string}[]`, reconciliation differences and missing opening evidence. Commit is permitted only when conflicts are explicitly resolved, totals reconcile and mode/version still match. Never infer opening balances from monthly inflow minus outflow.

`MonthlyProjectionResponse`: `month:Month`, `sourceMode:SNAPSHOT|LEDGER`, `sourceRevision:string`, `monthlyRecordId:Id|null`, `record:MonthlyRecordResponse|null` using the legacy adapter, `fieldBasis:map<string,Evidence>`, `projectionStatus:CURRENT|STALE|BLOCKED`, `scoreMethodologyVersion:string`. Missing COGS stays null; unimplemented obligations/inventory cannot be supplied as zero. Mapping period flows and closing stocks is explicit in the master plan.

Example request `{cutoverMonth:"2026-11",baseCurrency:"PKR",openingBalances:[{accountId:"uuid-cash",amount:{amount:"1000.00",currency:"PKR"}}],openingObligations:[],inventoryOpeningSnapshot:null,previewVersion:"preview-1",policyVersion:"pending"}` → preview conflict if November already contains a manual snapshot. No automatic replacement. Projection of an approved October opening 1000, inflow 300, outflow 100 yields closing cash 1200 only for the scoped cash accounts; revenue is determined separately.

Transitions: legacy months remain SNAPSHOT; prospective months at/after approved cutover become LEDGER; reversal does not change mode. Backdating/cutover rollback/closed-period adjustments require P01/P02 decisions. OWNER configuration capability plus step-up review can be proposed; projection jobs run only for an authorized tenant-bound system scope. Errors add `cutover_conflict`, `opening_balance_unreconciled`, `projection_overflow`. Tests: repeated projection identical, no snapshot-plus-ledger sum, snapshot manual-write protection, future-five-record rescore parity, null fields, reopened period, failed scoring rollback, OCR routing, migrated V17 fixtures. C02 is blocked on C01 and policy freeze.

## C03 Business configuration and module resolver

**Interface:** `configuration.service.BusinessConfigurationService` and `ModuleResolver`; `GET/PUT /api/v2/configuration`, `POST /api/v2/configuration/preview`. B extends business onboarding/profile without replacing identity. Existing scoring business types remain `trade|manufacturing|services|retail`; project-based operation is an operating profile/preset, not an unapproved fifth scoring type.

`ConfigurationUpdate`: `operatingProfile:MANUFACTURING|RETAIL_TRADE|SERVICES|PROJECT_ORDER`, `operatingAnswers:object` (closed, versioned schema), `requestedModules:string[]`, `terminology:{project:string,customer:string}|null`, `version:int`. `ConfigurationResponse`: same fields plus `businessId:Id` (response only), `resolvedModules:string[]`, `unavailableModules:{key:string,reasonCode:string}[]`, `allowedActions:string[]`, `recommendedPresetKey:string`, `registryVersion:string`. Labels are localized display values, never category or financial keys. A module registry entry has `key`, dependencies, supported profiles, permission requirements, implementation availability and data-retention behavior.

Example `{operatingProfile:"PROJECT_ORDER",operatingAnswers:{},requestedModules:["projects","invoices"],terminology:null,version:1}` → module closure includes approved prerequisites, or returns an explicit unmet-dependency error; it never enables an absent service. Configuration mutation requires existing `BUSINESS_SETTINGS_MANAGE`; read requires active business plus documented minimum permission. Disabled modules preserve data/preferences and follow approved read/export policy. Reject dependency cycles, unsupported key, disabling a required dependency and stale version. Tests cover old business defaults, business switch, permission precedence, toggles preserving rows, dependency closure and en/ur labels. Finance recognition is unaffected; changes to scoring fields follow existing methodology/change control.

## C04 Counterparties, obligations and payments

**Interface:** `obligations.service.ObligationService`, `payments.service.PaymentAllocationService`; `POST/GET /api/v2/counterparties`, `GET /api/v2/obligations`, `POST /api/v2/payments`, `POST /api/v2/payments/{id}/allocations`. B F04 invokes internal `createFromDocument` within the same transaction as issue/approve. No unauthenticated integration API is introduced.

`ObligationCommand`: `source:SourceRef`, `direction:RECEIVABLE|PAYABLE`, `counterpartyId:Id`, `issuedOn:Date`, `dueOn:Date`, `original:Money`, `fxLockId:Id|null`, `projectId:Id|null`, `recognitionPolicyVersion:string`. `PaymentCommand`: `paidOn:Date`, `accountId:Id`, `counterpartyId:Id`, `direction:RECEIPT|PAYMENT`, `original:Money`, `settlementQuoteId:Id|null`, `allocations:{obligationId:Id,amount:Money}[]`. Allocation amount is expressed in the obligation currency; mixed currency requires C09 conversion facts, never arbitrary client rates.

`ObligationSummary`: `obligationId`, source and counterparty IDs, `original:Money`, `allocated:Money`, `credited:Money`, `outstanding:Money`, `status:OPEN|PARTIAL|SETTLED|CANCELLED`, `dueOn`, `version`, evidence. `PaymentReceipt`: `paymentId`, `postingEventId`, applied allocations, `unallocatedAdvance:Money`, evidence. Outstanding belongs solely to A. Invoice status derives settlement from this response and never subtracts payments independently.

Example issued amount 1000, valid credit 100, allocation 300 → outstanding 600, PARTIAL; a receipt of 350 allocated 300 leaves advance 50 only if P03 allows it. Issue has **no cash movement**. Revenue/expense recognition at issue is P04, not inferred from this no-cash invariant. Cancellation with settled allocations requires a reviewed credit/refund workflow; no deleting paid obligations. Errors: `over_allocation`, `currency_mismatch`, `settled_source`, `counterparty_mismatch`. Proposed settlement-specific write capabilities cannot inherit MANAGER rights by accident. Tests: partials, one-day overdue boundary, overpayment/advance/refund, duplicate issue/payment, concurrent allocations, invoice-to-obligation reconciliation, cross-tenant links and cutoff timezone. Dependent production F04 completion waits for C04.

## C05 Project cost attribution

**Interface:** `projects.service.ProjectFinancialService`; `GET /api/v2/projects/{id}/financials`, `POST /api/v2/projects/{id}/attributions`, budget revision endpoints. B owns project IDs, cost attribution and financial rollup; A provides canonical posted facts and consumes approved plans.

`AttributionCommand`: `source:SourceRef`, `projectId:Id`, `categoryId:Id`, `allocatedBaseAmount:Decimal`, `allocationPolicyVersion:string`, `version:int`. Signed amount must match the direction of the canonical source effect. Aggregate allocation across projects cannot exceed the source effect; a partial allocation leaves a visible unallocated remainder. `ProjectPlan`: `projectId`, `budgetRevision:Id`, `currency`, `lines:{lineId,categoryId,quantity:Decimal|null,plannedAmount:Money,expectedOn:Date|null}[]`, `status:DRAFT|APPROVED|SUPERSEDED`.

`ProjectFinancials`: `projectId`, `budgetRevision:Id|null`, `recognizedRevenue:Money|null`, `recognizedCost:Money|null`, `profit:Money|null`, `marginPct:Decimal|null`, `budgetVariance:Money|null`, `costBreakdown:{categoryId,amount:Money,sourceRefs:SourceRef[]}[]`, `cashReceived:Money|null`, `cashPaid:Money|null`, evidence. Paid cash and recognized profit are separate fields. Zero revenue yields null margin with a reason. Inventory issue cost and commission cost are read from C07/C08, not recomputed or copied into expense facts.

Example approved budget 1000, eligible actual cost 800 → cost variance 200 favorable under documented `budget - actual`; recognized revenue 1200 → profit 400 and margin 33.333…% using frozen display rounding. Never add the budget 1000 to actual cost 800. Creation and attribution permissions must be explicit; C08 row scope applies before aggregates. Errors: `allocation_exceeds_source`, `source_not_posted`, `plan_revision_stale`. Tests: retries, reversal removes effect once, split allocation conservation, unallocated cost disclosure, revenue-zero/null, project tenant mismatch, paid versus recognized sample/commission treatment. Blocked integrated outputs return partial basis until sources exist; no false zero.

## C06 Cash plan and funding gap

**Interface:** A `projectcash.service.ProjectCashPlanService` and `FundingGapCalculator`; `PUT /api/v2/projects/{id}/cash-plan`, `POST /api/v2/projects/{id}/funding-scenarios`. B supplies approved C05 plans and displays results.

`CashPlanCommand`: `projectId`, `budgetRevision:Id`, `openingAvailableCash:Money|null`, `lines:{id:Id,sourcePlanLineId:Id|null,direction:IN|OUT,amount:Money,expectedOn:Date,settledSourceRefs:SourceRef[]}[]`, `version:int`, `policyVersion`. `ScenarioRequest`: base plan version plus typed timing/amount overrides; never a posting command. `FundingGapResult`: `daily:{date,plannedNet:Money,actualNet:Money,cumulativeAvailable:Money}[]`, `peakFunding:Money|null`, `peakDate:Date|null`, `recoveryDate:Date|null`, `assumptions:string[]`, evidence.

Proposed formula after approval: `max(0,-min(cumulative available cash))`; starting cash allocation and same-day ordering must be explicit. Example opening 0, day 1 outflow 200, day 3 inflow 300 → peak 200, recovery day 3. A settlement linked to a planned inflow replaces the settled portion of that plan, not an additional inflow. Unscheduled residual remains planned. No receipt date → unavailable timing, not today's date. Errors: `missing_plan_dates`, `currency_basis_missing`, `stale_plan`, `settlement_exceeds_plan`. Read/write rights inherit approved project scope; restricted users must never receive business-wide cash. Tests: partial actual replacement, advance once, no recovery date, equal-date grouping, negative opening policy, horizon boundaries, business/project scope and deterministic scenario nonmutation.

## C07 Inventory and COGS

**Interface:** B `inventory.service.InventoryValuationService` and `InventoryMovementService`; `POST /api/v2/inventory/movements`, `GET /api/v2/inventory/valuation`, internal recognized-cost feed to C01/C05. A alone projects the accepted COGS effects into MonthlyRecord.

`MovementCommand`: `itemId:Id`, `kind:RECEIPT|ISSUE|RETURN|ADJUSTMENT`, `quantity:Decimal`, `occurredOn:Date`, `source:SourceRef`, `projectId:Id|null`, `originalCost:Money|null`, `fxLockId:Id|null`, `reversesMovementId:Id|null`, `version:int`, `valuationPolicyVersion:string`. Quantity positive with direction from kind; adjustment requires separately approved sign/reason. Receipt requires known cost; issue cost is server calculated. `MovementResult`: `movementId`, `onHand:Decimal`, `weightedAverageUnitCost:Money|null`, `inventoryValue:Money`, `recognizedCost:{source:SourceRef,projectId:Id|null,amount:Money,classification:string}|null`, `postingEventId:Id|null`, evidence.

Proposed WAC receipt rule: `(old value + approved landed receipt cost)/(old quantity + received quantity)`. Example 10 units value 100 + 10 units value 200 → 20 units value 300, WAC 15; issue 4 → recognized eligible cost 60, residual value 240. Returns, negative stock, zero quantity, backdates, freight and whether an issue is WIP or COGS require P06. An issue cannot automatically mean sale. No purchase-expense-plus-COGS double count.

Transitions are immutable posted movement with compensating return/reversal; lock item valuation row and source receipt atomically. Errors: `insufficient_stock`, `valuation_unavailable`, `backdated_movement_blocked`, `cost_policy_missing`. New inventory rights and C08 project scope need review. Tests: concurrent issues, fractional units, precision residual, returns at approved historical cost, same source retry, project cost once, inventory value reconciliation and V17 upgrade. Contract is draft; numerical WAC example is a test proposal, not production financial signoff.

## C08 Commission lifecycle and sales scope

**Owner A; B reviewer and consumer.** `commission.service.CommissionService`, `SalesScopeService`; `/api/v2/commissions` and policy-approved earn/approve/pay/reverse actions. A owns SALESPERSON membership extension, server row filtering and authorization of assigned customers/orders. B's UI filtering is only presentation.

`CommissionBasis`: `salespersonMembershipId:Id`, `source:SourceRef`, `projectId:Id|null`, `ruleVersion:Id`, `eligibleAmount:Money`, `basisDate:Date`, `recognitionTrigger:string`. `CommissionCost`: `commissionId:Id`, `source:SourceRef`, `projectId:Id|null`, `recognizedAmount:Money`, `paidAmount:Money`, `status:CALCULATED|EARNED|APPROVED|PAID|REVERSED`, `postingEventId:Id|null`, evidence. ## C09 FX and settlement

**Interface:** A `fx.service.FxRateLockService`, `SettlementService`; `POST /api/v2/fx/rate-locks`, `POST /api/v2/settlements/preview`, `POST /api/v2/settlements`. Freeze original/base fields before F01/F04 even if live FX arrives later.

`RateLockRequest`: `originalCurrency`, `baseCurrency`, `rate:Decimal`, `effectiveOn:Date`, `sourceName:string`, `sourceRef:string|null`; rate direction is **base units per one original unit**, positive. `RateLock`: `id`, request fields, `lockedAt`, immutable. `SettlementRequest`: `obligationId`, `originalSettled:Money`, `grossReceivedBase:Money`, `feeBase:Money`, `accountId`, `settledOn`, `rateLockId`, `version`. Net cash is derived, never accepted as a competing total. `SettlementResult`: `carryingBaseReleased`, `grossBase`, `feeBase`, `netCashBase`, `realizedFx:Money`, `paymentId`, `eventId`, evidence.

Synthetic receivable example: USD 100 carrying PKR 28000; gross receipt PKR 28500; fee 500 → net cash 28000; realized gain 500 under approved receivable sign policy and fee cost 500. Do not net away the gain/fee evidence. Payables require inverse gain/loss logic. No rate lookup using today's rate for old events. P10 determines partial release rounding, credit/reversal rates, fee category and noncash revaluation (not assumed in scope). Errors: `rate_missing`, `currency_pair_mismatch`, `settlement_negative_net`, `locked_rate_conflict`. Tests: partial rounding conservation, receivable/payable signs, inverse rate rejection, fee once, immutable locks, duplicate settlements and base/original reports. Authorization follows approved posting/settlement permissions.

## C10 Dashboard workspace

**Interface:** B `dashboard.workspace.WorkspaceQueryService`, `WorkspaceResolver` and `WorkspacePreferenceService`; `GET /api/v2/workspace`, `PUT /api/v2/workspace/preferences`, `POST /api/v2/workspace/reset`. Reuse `DashboardService`/score/evidence providers; C11 can expose existing authoritative metrics incrementally.

`WorkspacePreferences`: `presetKey:string`, `widgets:{key:string,order:int,size:SMALL|MEDIUM|LARGE,hidden:boolean}[]`, `version:int`, `registryVersion:string`. Tenant/user IDs are server-derived; unique `(business_id,user_id)`. `WorkspaceResponse`: permitted registry entries (`key`, supported sizes, localized title key, capability/module requirements), effective layout, summary map of evidence-wrapped DTOs, `preferencesVersion`, `presetVersion`. ## C11 FinancialQueryFacade

**Owner A; orchestration B.** A `financialquery.service.FinancialQueryFacade` offers typed read-only functions: `getCashPosition`, `getOverdueReceivables`, `getUpcomingObligations`, `getProjectFinancials`, `getProjectFundingGap`, `getMarginDrivers`, `getFxSettlementImpact`. Each only registered when its owner service exists. HTTP transport, if needed, is `POST /api/v2/financial-queries/{toolName}` with CSRF despite read-only semantics. B's provider adapter cannot invoke repositories, raw SQL or arbitrary URLs.

`QueryRequest`: `arguments:object` validated against per-tool closed JSON Schema (`additionalProperties:false`), `asOf:Date|null`, `period:{from,to}|null`, `locale:en|ur`. Tool-specific IDs are UUIDs; bounds and permitted intervals are mandatory. `QueryResult`: `toolName`, `contractVersion`, `status:AVAILABLE|PARTIAL|UNAVAILABLE|RESTRICTED`, `data:object|null` with typed Money/Decimal values, `reasonCode:string|null`, `evidence:Evidence`, `queryId:Id`. A scope token/context is server-derived and not serialized into model input.

Example `getProjectFinancials` arguments `{projectId:"uuid-project"}` returns C05 DTO, period and source refs. Missing attribution returns PARTIAL/null affected ratios, never an estimated balance. Tool output must numerically equal the ordinary domain endpoint for the same scope, date and revision. Query state has no financial transitions; only rate-limited audited execution. B validates tool schema/version/evidence freshness, routes intent, bounds steps/retries, and generates a response grounded only in approved fields. Tool/document text is data, never a new instruction. Reauthorize every tool call and after business switch; redact disallowed sources before provider routing.

Errors: unknown/unavailable tool, invalid argument, rate cap, stale evidence, provider timeout (B boundary). No credentials, arbitrary query execution or autonomous mutations. Tests: exact domain parity, cross-business/project/salesperson denial, membership revocation, prompt injection, fabricated number rejection, missing data, stale snapshot, English/Urdu, multi-step cap and cost limits. Existing OCR is not C11 or an LLM provider. Financial tools can precede W6 in slices when their real services are ready; full catalog remains blocked by those services.

## C12 API and i18n conventions

**Owner B, reviewer A; each feature owner authors their own endpoints/translations.** Extend `frontend/src/lib/api/client.ts`, domain API modules, `contracts.ts`, `lib/i18n/errors.ts`, `labels.ts` and translation dictionaries. Preserve generation-based cancellation on business/session changes, `credentials:'same-origin'`, CSRF acquisition, non-replayed writes, explicit demo boundary and loading/error/empty/no-data states.

New DTO fields follow the shared rules above. An API adapter translates legacy numeric money to presentation without changing stored values; no global search/replace migration to strings. `LocalizedMessage={key:string,args:Record<string,string>}` carries display substitutions, not translated enum keys. Validation field paths remain stable (`lines[0].quantity`); server error codes map to en/ur dictionaries with safe fallback. Domain keys/categories remain language invariant. Example 409 `{status:409,error:"stale_version",message:"This record changed. Reload it before saving."}` maps to the relevant locale and preserves unsaved edits; the client must not silently repost.

Registry and schema changes are versioned with producer and consumer fixtures. Contract tests cover all status/nullability cases, malformed amount strings, invalid IDs/dates, error localization, enum expansion, no client business ID, cookie/CSRF propagation, tenant-switch cancellation, English/Urdu/RTL text and mobile forms.
